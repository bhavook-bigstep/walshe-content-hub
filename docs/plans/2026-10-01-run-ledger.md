## Chosen re-entry approach (MANAGER decision, RE-ENTRY B)

**Chosen: Approach 2 — risk-first vertical slice**, grafted with the strongest ideas from Approaches 1 and 3.

**Why this one.** All three candidates agree on the fundamentals (extend the existing FastAPI + `lib/studio`, fix the asset-auth hole first, fix docker, build the real Next.js UI, add a Playwright smoke). They differ only in **ordering and rigor**, and the decisive fact is in the Blockers section above: **the prior run died on budget**, and the single biggest budget-burner was **Fabric.js under Next.js**. Approach 2 is the only one that retires the two riskiest unknowns — the asset-auth fix and the Fabric-in-Next spike — *first, while the budget is intact*, with each step a green gate. Approach 1 builds the studio **last** (so the hardest unknown is attempted when the budget is most depleted — the exact way run #1 stalled). Approach 3 is the most correct on paper but is the heaviest (it self-estimates 2–3 iterations and "web UI ≈ 75% of effort"), so it carries the highest re-stall risk on the same 4×2 budget.

**What was grafted in (so the choice is strictly dominant):**
- *From Approach 3:* a single **shared visibility predicate** reused by both `assets` and `catalog` (the two access rules can't drift — materially strengthens Contract 1); **path-traversal rejection** on `object_key`; one **negative e2e test** (Agent → Admin URL redirects); **proportionate loading/empty/error states** per screen (kept proportionate, not the full failure-mode matrix, to protect budget); and a **`make verify`** aggregate gate + short README runbook.
- *From Approach 1:* the "**build the studio so a partial studio can't block the other screens**" framing, and **one small commit per gate** so every green gate is a resumable checkpoint.

**Decisions locked up front (resolving where the candidates disagreed):**
- Asset images render via **authed-fetch → blob URL**, *not* a Next cookie-proxy route — no API change, deterministic (Approaches 2+3 beat Approach 1 here).
- Playwright e2e runs against a **production build** (`next build && next start`), not `next dev` — kills cold-compile flakiness.
- Hidden/unknown asset keys return **404, not 403** — existence can't be probed.

**The trade-off, stated plainly.** Risk-first means the **clickable screens a human verifies at gate ⏸G arrive later in the sequence** than Approach 1's screens-first ordering — the UI that proves "there is a product" is not the first thing built. We accept that cost because (a) the re-entry goal is a *verifiable* slice **and** the prior run stalled on budget, so cutting the odds of a second stall on the hardest unknown outweighs seeing screens a little sooner; and (b) we mitigate the cost directly — the design loop is **capped at 1–2 iterations** and there is a **commit per gate**, so even a partial run lands a correct, runnable product (auth-fixed, docker-fixed, studio-proven) rather than pretty screens over an unfixed security hole.
