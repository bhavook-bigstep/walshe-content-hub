### Brainstorm outcome — pipeline architecture (B1)

Decision question: how to turn an uploaded PDF/image into 1..N draft entries via the AC16 seam while staying deterministic (Contract 4).

- **A — Two-stage chained LLM (extract → structure)** *(chosen)*: `complete()` call #1 extracts free-form tourism facts from locally-extracted PDF text (pypdf) / image; `complete()` call #2 maps facts → JSON array of draft entries, parsed like `builder._parse_ops`, deterministic stub fallback on both. Maps 1:1 to charter decisions #2/#3 and to the proven `build_design` shape (`apps/api/app/ai/builder.py:138`) — smallest diff, cheapest determinism. *Source:* two-step decoupling improves formatting reliability — python.langchain.com extraction docs — https://python.langchain.com/docs/use_cases/extraction (accessed 2026-10-06).
- **B — Single-stage (document → JSON entries in one call)**: fewer calls, lower latency/cost, but monolithic extraction underperforms on complex docs and couples concerns. *Source:* same langchain docs note two-stage outperforms monolithic on complex extraction.
- **C — Deterministic-first hybrid (local pypdf + regex/gazetteer pre-parse grounds one structured call)**: maximizes grounding of dates/locations, least hallucination, but more code + heuristic brittleness for a PoC. *Source:* Extract Text from a PDF — pypdf — https://pypdf.readthedocs.io/en/latest/user/extract-text.html (accessed 2026-10-06).
- **D — Generalize Builder's tool-use loop (agent calls `create_draft_entry` 1..N times)**: most "agentic", but repo's Builder is actually one-shot JSON-ops, not a multi-turn tool loop; a true loop is harder to make deterministic under the stub and heavier than a PoC needs. *Source:* **No source found — this is an AI-generated idea.**

**Chosen: A. Trade-off accepted:** two `complete()` calls per document (~2x latency/cost vs B), bought in exchange for reuse of the proven stub-fallback shape, cleaner full-field inference (AC66) in call #2, and better reviewability (Contract 4). For the stub path both stages are deterministic, so the extra call costs nothing in tests.

## Open assumptions / deferrals
- PDF text via pure-python `pypdf`; fall back to stub extraction if unavailable (keeps tests hermetic).
- Images sent as the "document"; stub path seeds extraction from bytes/filename (no real vision call in PoC).
- Drafts attach to the provider's single catalog (`catalogs/mine`, AC49); no new catalog created.
- "AI-created" marker is a new additive field on `CatalogEntry`.
- Deferred: OCR of scanned PDFs, per-provider vision tuning, async bulk ingestion, auto-publish (out of scope).

### Brainstorm outcome — v2 architecture (B-v2)

Decision question: how to run the import asynchronously (AC71), extract+store images (AC72), create
entries + attach images via a server-validated LLM tool-call path (AC73), and surface jobs on a
navbar bell (AC74) — while keeping Contract 4 (deterministic/hermetic tests) and Contract 1 (drafts
only) intact. The charter already locks the big choices (in-process bg task + `Job` table + polling ·
PyMuPDF · LLM tool-call · bell), so the brainstorm is over the *orchestration seam* and *loop shape*.

- **A — `BackgroundTasks` + one-shot server-validated tool-ops (builder-style)** *(chosen)*: `POST
  …/import` validates type/size and **reads the bytes synchronously**, inserts a `Job(status=queued)`,
  schedules the extraction via FastAPI `BackgroundTasks`, and returns **202 {job_id}**. The task opens
  its **own** `Session` (from `app.state` sessionmaker — the request session is closed after the
  response), flips `queued→running`, runs `extract_entries` + image extraction, then the agent emits a
  single JSON of ops (`create_entries`, `attach_image`) that the server validates one-by-one (reuse
  `_normalize_entry`/`EntryCreate` + verify `image_ref` is a real extracted image) before persisting
  drafts, and sets `done`/`failed`. Mirrors the proven `builder._parse_ops` one-shot-ops + stub
  fallback, so determinism is free (stub path runs the same validated ops; tests call the task fn
  directly). Smallest diff; reuses `/assets/{key:path}` for serving. *Source:* Background Tasks —
  FastAPI (tiangolo) official docs — https://fastapi.tiangolo.com/tutorial/background-tasks/ (accessed
  2026-10-06): BackgroundTasks run after the response is returned — the exact "202 now, work after"
  shape AC71 needs. Image pattern: Recipes: Images — PyMuPDF docs —
  https://pymupdf.readthedocs.io/en/latest/recipes-images.html (accessed 2026-10-06):
  `page.get_images()` → xref → `Document.extract_image(xref)` yields image bytes + ext, no Pillow dep.
- **B — Dedicated worker thread + true multi-turn tool-use loop**: a daemon thread per job with its own
  session runs a real provider tool-use loop (model calls `create_entries`/`attach_image` over several
  turns, server executes + returns tool results). Most "agentic" and survives the response lifecycle
  cleanly, but the repo's Builder is one-shot JSON-ops (not a multi-turn loop), so this is more code,
  thread/session-lifecycle risk, and harder to pin deterministic under the stub for Contract 4. *Source:*
  **No source found — this is an AI-generated idea.**
- **C — `asyncio.create_task` fire-and-forget coroutine + one-shot ops**: schedule the job as a bare
  asyncio task instead of `BackgroundTasks`. Slightly more control over concurrency, but a blocking
  LLM/pypdf/PyMuPDF call would block the event loop unless offloaded to a threadpool, and an unawaited
  task can be GC'd/swallow exceptions — strictly worse than `BackgroundTasks` (which already runs sync
  fns in a threadpool) for a single-document PoC. *Source:* Background Tasks — FastAPI (tiangolo) —
  https://fastapi.tiangolo.com/tutorial/background-tasks/ (accessed 2026-10-06): recommends
  BackgroundTasks for post-response work; Starlette runs non-async task fns in a threadpool.

**Chosen: A. Trade-off accepted:** `BackgroundTasks` runs in-process and does **not** survive a server
restart — a job left `running` at crash stays stale (acceptable for a PoC; a trivial startup sweep or a
"stale after N min → failed" read can mitigate later). It occupies a Starlette threadpool worker for the
LLM call (fine at one-document concurrency). Bought in exchange for the smallest diff, reuse of the
proven one-shot-ops + stub-fallback shape (Contract 4 is free), and no new async infra.

**Sub-decision — image lib (AC72):** charter mandates **PyMuPDF** (self-contained, no Pillow). Noted
alternative: the already-present **`pypdf`** dep also extracts images (`page.images`,
https://pypdf.readthedocs.io/en/latest/user/extract-images.html, accessed 2026-10-06) → **no new dep**,
but needs Pillow for several encodings and is less robust on damaged PDFs. Recommend following the
charter (PyMuPDF) for robustness; flag pypdf-reuse only if adding the dep is contested at plan time.

4. Image serving already exists: `GET /assets/{object_key:path}` + `can_read_object` (assets.py:154).
   Cover reuses `CatalogEntry.cover_object_key` (catalog.py:144); extras become `Asset` rows
   (catalog.py:184). Store under an `entries/{id}/...` key like the existing cover route.
5. Bell lives in the shared `AppShell` top bar (components/shell/AppShell.tsx) rendered by the provider
